InfoCell: the concept

What an info cell is, how a grid becomes cells, how a rule is searched for, and which layers sit on top of each other. This page is about the ideas, not the code.

Part 1The cell world

Everything is a cell: a number, a pixel, a grid, an object, a rule. A cell is a set of slots, and each slot holds another cell. There are only a few primitive instructions:

InstructionWhat it doesWhat is true afterwards
SET(cell, key, value)puts value into the slot keyGET(cell, key) == value
GET(cell, key)reads the slotnothing changes
NEW(type)creates a cellone more cell exists
ERASE(cell, key)removes the slotHAS(cell, key) == false

The key idea is to think in time: the world before an instruction and the world after it. After SET(cell, key, value), the fact GET(cell, key) == value holds. Learning turns this around: given a fact that must hold afterwards, which instructions make it true?

A value written as @c2 is a link to cell c2. Links are how cells form a world: a pixel's up slot holds the pixel above it, and an object's pixels slot holds its pixels.

Data cells and active cells

A data cell only holds slots. An active cell is an instruction: activating it changes the world, and it reports a result in its own value slot. There is no central processor; every active cell is a small one.

Types are cells too

A type says which slots its cells have. Pixel, Grid, Number and List are types, and so are the instructions themselves. The type graph is the meta level: the cells that describe cells.

New cells

NEW is what makes the world open-ended. Without it, a fixed set of cells has finitely many states. With it, the world can grow: new objects, new rules, new concepts.

Part 2 · From grid to program

One ARC task, followed from the grid to the learned rule. The example is a real toy task: every red pixel grows a yellow cross.

2.1Grids become info cells

One pixel, one cell

Each input pixel is a Pixel cell with the slots x, y, color and the links up, down, left, right. The Grid cell holds width, height and the list of pixels.

Read with GET

Every question about the input is a GET. GET(GET(p, down), color) is "the color below p". The cells are read-only: an input is never changed.

The output is a postcondition

The output grid is not executed. Each output pixel is a fact to explain: GET(out(2,1), color) == yellow. Learning means finding what makes all of these facts true at once.

2.2It learns the program

1 · Find what changed

Compare each output with its input. The circled pixels are new: 4 in the first pair, 3 in the second, where the red pixel touches the border. New pixels guide which rule to try first. They are not the whole test: a program is accepted only if it rebuilds the entire output, so a pixel that looks unchanged must be explained too.

2 · Perceive a layer above

Same-color neighbours are grouped into object cells with slots like color, size, position and holes. The rules can then talk about objects as well as pixels.

3 · Let hypotheses compete

Every rule family proposes a program. A program is kept only if it reproduces every training output exactly. The shortest of those wins: compression decides.

HypothesisReads (GET)On the training pairsResult
Pixel table on {color}the pixel's own colorblack becomes black, and black becomes yellow: a contradictionrejected

The winning rule is the solver's real output for this task: objects[single color] addition: outline 4. Its next two candidates were the same rule with diagonal and multi-color objects. Every part of it is visible in the examples: what counts as an object, what is added, and in which color.

2.2bCells built on cells

A second real task, with bigger objects: the largest object turns green. It has three training pairs, and the solver solves it with table[{is largest object}]. Below is the first input and every cell the solver builds for it. Press Replay to watch the object cells being born, or click an object cell to see its pixels.

Birth of an object cell

Perception scans the Pixel cells in reading order. The first colored pixel that no object owns yet triggers NEW Object. Then it follows up, left, right and down: every neighbour with the same color joins the same object. When nothing more joins, the object is complete.

Slots are computed, not given

An object's slots, such as size, width, top and touches border, are GETs over its member cells. Comparing objects adds relation slots like largest. Each slot is a new fact that no single pixel holds.

The rule reads down the layers

The rule cell asks each pixel: GET(GET(p, object), largest), meaning "is my object the largest?" Yes → green, no → keep my color. The rule fits all three training pairs, and nothing shorter does.

Every cell here is one the solver really computes. Grouping same-colored 4-neighbours is one of 7 ways it parses a grid. The others are diagonal neighbours, multi-color objects, all pixels of one color, background regions, rows and columns. Each parse is tried, and the rule decides which one is used.

2.3The program runs on the test input

Perceive

The test input becomes cells, just as in step 1. Perception finds two single-color objects, both red.

Execute

For each object, the program GETs the 4 neighbours of its cells. Each neighbour that is free background gets SET(out(x,y), color, yellow).

Check

The result matches the expected test output, so the task counts as solved. Every SET can be traced back to a rule and an object.

2.4When the output is bigger: new cells

The red-cross task only recolors pixels that already exist. A 2×2 input with a 4×4 output is different: 12 of the output pixels have no input pixel of their own. Each one has to be created with NEW, and the program must say where its color comes from. The simplest answer is a link to a parent cell in the input. Click any output pixel to see its parent.

Scale up

The parent is (x div 2, y div 2), so every input cell gets a 2×2 block of children. The solver learns this as scale up.

Tile

The parent is (x mod 2, y mod 2), so the whole input repeats. The solver learns this as tile with symmetries. Both toy tasks are solved.

Why a link compresses

Listing 16 output colors costs 16 × log₂10 ≈ 53 bits per example. "Copy the parent at x div 2" costs a few bits once and fits every example.

3×3 → 9×9: a cell with two parents

This is ARC training task 007bbfb7. Every colored input pixel becomes a full copy of the input, and every black one becomes a black 3×3 block. Each of the 81 new cells needs two parents:

  • a block parent (x div 3, y div 3), which decides whether there is a copy here;
  • an inner parent (x mod 3, y mod 3), which gives the color.
Block parent colorInner parent colorNew cell color
blackanyblack
orangeblackblack
orangeorangeorange

The rule is a 3-row table

out(x,y) = T[ in(x div 3, y div 3), in(x mod 3, y mod 3) ]. It is the same kind of pixel table as in step 2, except that the two features are two different parents.

How the solver does it

A built-in family, self-similar, does exactly this. It failed at first because it took the most frequent color, orange, as background. With the same rule as everywhere else (0 if present), it now solves 007bbfb7.

The general version

The family is hand-written for this one shape. The general form would let a new cell keep both parent links and let the pixel table read features from both. Then the same 3-row table would be learned rather than built in.

This is where cell creation and compression meet. A new cell only exists if the program creates it. It is worth creating only if the links it carries let the rule be shorter than listing its color. The same test can decide when a whole new concept cell is worth adding to the library.

Part 3Searching

Learning is search: among many candidate explanations, find the ones that fit every example, and prefer the shortest. There are two ways to search.

Backward: which tool makes the fact true?

Start from the fact that must hold, after == value, and look for a tool among the existing operations that produces it from the value before. A tool counts only if it explains every example; it is then applied to the test input.

These are real results of the original InfoCell ToolFinder. In 1, 2, 1, 2 no single tool explains both steps: alternation needs two operations, or a memory of the step before.

Forward: build programs, keep the shortest that fits

Combine steps into programs, run each one on the examples, and keep those that reproduce every output exactly. Among those, the shortest description wins. Chaining steps grows fast, so only a beam of the most promising states survives each level.

Without a beam

Every extra step multiplies the count by the number of steps: depth 5 with 74 steps is over two billion programs.

With a beam

Each level only expands the states that survived, so every level costs the same. Depth gets cheap; what limits it is whether the right intermediate state survives.

Depth is not the point

People solve ARC tasks in one to three moves, but each move is a big one. Deep chains of tiny steps are the opposite of compression. Better steps help more than deeper search.

Part 4The layers

Each layer is made of cells that are built from the cells below it. A rule can read any layer.

Hand-written means the kinds of things the layer contains were typed in: what an object is, what an outline is. Learned means the system chooses them from the examples. Emergence is when a lower layer produces the vocabulary of a higher one on its own.

Part 5A formal system

In Gödel, Escher, Bach a formal system is an alphabet, axioms and rules of inference; theorems are what the rules can derive. The cell world maps onto it directly:

Formal systemCell world
a stringa world state: cells and their slots
axiomsthe initial world: the types, the input grid
rules of inferencethe primitive instructions: SET, GET, NEW, ERASE and the control instructions
theoremsthe world states that can be reached
is X a theorem?can a world be reached where GET(cell, key) == value?
finding a derivationfinding the tools that make it true

Positive examples only

From valid strings alone a grammar cannot be guaranteed (Gold, 1967). But the shortest description the examples fit is still a good guess: from 36 theorems of the pq-system the pattern x p y q x y, Hofstadter's own rule, comes out.

Figure and ground

Holes and background regions are information too. An object with holes is a figure; its holes are negative-space objects, linked to their container. The inside of a ring only exists if figure and ground connect in opposite ways.

Repetition

Two unrelated problems miss the same idea: multiplication in the tq-system and "repeat this shape until the edge" in ARC. A primitive for repetition is a candidate axiom, not one more hand-written rule.

Open ideas

  • Create a cell when it shortens the description. A pattern that repeats becomes a cell; a concept that saves nothing is dropped.
  • Pixels in several objects. Parts inside wholes, and the pixel where two lines cross.
  • Negative space as objects. Holes as cells linked to their container.
  • Edges that wrap around for some colors or shapes and not for others, chosen by the examples.
  • A learned drawing order when two rules paint the same pixel.
  • Repetition as a primitive, so that loops can be composed instead of written.
